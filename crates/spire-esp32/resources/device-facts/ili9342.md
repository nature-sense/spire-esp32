# ILI9342 — protocol facts

Part number `ili9342` (ILI9342C / ILI9342E). The **ILI9342** is an SPI panel controller — the
CoreS3's 320 × 240 IPS — driven command by command: a command byte, then its parameters or data, on
the component's `bus_command` / `bus_data` seam, never a register read.

Derived from `spire-idf` `components/ili9342/src/ili9342.cpp`, whose init tables are transcribed from
Espressif's `esp_lcd_ili9341` defaults and the CoreS3 BSP's `ili9342e_init_cmds.h` (Apache-2.0). This
is an **implementation, not the datasheet**: confirm the electricals against it.

## The command set

- `0x01` `SWRESET` — software reset (not the reset *line*: that is the board's)
- `0x11` `SLPOUT` — leave sleep mode (a panel wakes up asleep)
- `0x21` `INVON` — colour inversion **on**; this panel's own requirement, not an option. Without it
  every colour comes out as its complement.
- `0x29` `DISPON` — display on
- `0x2A` `CASET` — column address set; `0x2B` `PASET` — page address set: two corners each, **high byte
  first**, both *inclusive* (`[x0, x1]`)
- `0x2C` `RAMWR` — memory write; consumes the pixels the window points at
- `0x36` `MADCTL` — memory access control: the frame's orientation and colour order
- `0x3A` `COLMOD` — pixel format

## The power-on sequence

The part's tuning — power control, timing, gamma — is the *vendors'*, not this project's, and is sent
as `(command, parameters, delay_ms)` rows. Espressif's defaults and the CoreS3 BSP's E table agree line
for line on the common block, so it has one copy; the **E revision** adds a second block of its own.
Both end with the frame — `MADCTL`, `COLMOD`, `INVON`, `DISPON` — each with the interval it wants.

The two values that are not tuning, because the glass is mounted in them:

- `MADCTL` = `0x08` — RGB element order (bit 3: the panel is wired BGR), no row/column exchange (bit 5),
  no mirroring (bits 7:6). A rotated display is a different order of drawing, not a different panel.
- `COLMOD` = `0x55` — 16 bits per pixel, RGB565, the format `flush()` names in its signature.

Two delays are the panel's, not rates: 20 ms after `SWRESET`, and 120 ms after `SLPOUT` and again
after `DISPON` — the charge pump needs it.

## A flush

Set the window (`CASET` then `PASET`, two corners each), then `RAMWR` and the pixels — two bytes each,
big-endian RGB565, and the count is the window's own area (`(x1-x0+1)*(y1-y0+1)*2`). The panel walks
the window itself, so a count that disagrees with it is a band that wraps onto the row below.

## What a bad frame looks like

- a reversed window (`x1 < x0` or `y1 < y0`) or no pixels → the driver refuses (`false`); the panel
  would take it without complaining — `CASET` with reversed corners is a window it declares and never
  fills — so the refusal has to be here, where the caller can still do something about it.
- a panel that stays silent, or answers on a bus that is not wired → `false` from the seam.
